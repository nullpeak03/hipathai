## 1. Executive summary

HiPath AI is a **credible, well-engineered MVP** whose *generation* pipeline is now production-grade, but whose *learning* pipeline is essentially unproven and whose *commercial* funnel is currently broken.

| Dimension | Grade | Verdict |
|---|---|---|
| Feature completeness (code) | **B+** | 5/5 core features implemented; Pro/billing intentionally absent |
| Feature completeness (validated) | **D** | Only 2 lessons have ever been completed in production |
| Stability | **B−** | Generation is fixed and fast now; 18% all-time job failure rate, 0 alerting |
| Security | **B** | No P0 exploit found; 2 launch blockers + 7 high-severity hardening gaps |
| Data integrity | **B−** | RLS enabled everywhere, but authorization is 100% app-level and unaudited |
| Test/CI maturity | **A−** | 431 tests, CI on every push, clean typecheck/lint/build; no E2E |
| Observability | **D** | PostHog only; no error tracker, no latency/token dashboards, no alerts |
| Monetization readiness | **F** | Pro cannot be bought; the waitlist endpoint returns 401 to every visitor |

### The three sentences that matter

1. **The product generates content well now.** Roadmap generation survived a real 8-phase/56-lesson run in 2m50s; the fixed lesson pipeline produced a complete 41-block lesson with 7 exercises in 62s, `missingParts: []`.
2. **Almost nobody has used it.** 29 users and 42 roadmaps exist, but the entire database contains **2 completed-lesson rows, 2 quiz attempts, 0 spaced-repetition rows, 0 mastery rows, and 0 capstone submissions**. The learning loop is code-complete and production-unverified.
3. **You cannot currently acquire a paying user.** `POST /api/pricing/waitlist` returns **401** to anonymous visitors because middleware default-denies every API route not on its public list. The Pro waitlist has collected 1 signup and is effectively closed.

**Recommendation:** do not broaden the feature surface. Fix the two launch blockers (waitlist, roadmap input clamps), then run a real 7-day dogfood of the learning loop with 5–10 users and instrument it. Everything else in this report is secondary to proving that a learner can finish a roadmap and come back.

## 2. Architecture as built

```
Browser (Next.js 15 App Router / React 19 / Serwist PWA)
   │  Clerk session cookie
   ▼
Middleware (Clerk)  ── default-deny for /api/*, CSP, HSTS, frame/nosniff headers
   ▼
Route handlers (45)  ── all DB access via SUPABASE_SERVICE_ROLE_KEY
   ▼                         (RLS is bypassed by design; ownership checked in code)
Supabase Postgres (28 tables)  +  Storage (private `tutor-images`)
   ▲
   │  Inngest (5 functions: roadmap, lesson, quiz, streak, sweep)
   ▼
NVIDIA NIM (hedged model fallback, deadline-based calls)
```

**Key architectural fact:** the browser only ever gets the Supabase **anon** key, and no Clerk→Supabase JWT exchange is configured. Therefore RLS policies scoped `to authenticated` are *never exercised at runtime*; the server service-role client bypasses RLS on every query. **Authorization is 100% hand-written route logic.** That is a legitimate pattern, but it means one missing ownership check is a full cross-tenant data breach, and 21 RLS policies provide no real defense-in-depth today.

**Strengths of the architecture**
- Server-only service-role key; no privileged client bundle (`src/lib/supabase/server.ts`).
- Ownership is checked explicitly in the sensitive paths reviewed: lessons (`src/lib/lesson-access.ts`), chat threads (`src/app/api/chat/threads/[threadId]/route.ts`), roadmap status (`src/app/api/roadmaps/status/[jobId]/route.ts`).
- Long work is correctly pushed to Inngest instead of held in a 60s request.
- AI calls have absolute deadlines and bounded retries (`src/lib/nim.ts`, `src/lib/ai-router.ts`).
- Security headers and a CSP ship from middleware; HSTS includes `preload`.

## 5. Findings

Severity: **P0** = launch/business blocker or exploitable cost/security hole · **P1** = must fix before growth · **P2** = fix in the next cycle · **P3** = hygiene.

### P0 — fix before any launch or outreach

#### P0-1. The Pro waitlist is unreachable by anonymous visitors
- **Evidence:** `src/middleware.ts:5-17` lists public routes; `/api/pricing/*` is absent. Lines 79-85 default-deny all other `/api/*` without a Clerk session. Live verification: `POST https://www.hipathai.me/api/pricing/waitlist` → **401** `{"error":"Unauthorized"}`. The route itself has no auth requirement and is designed for anonymous emails (`src/app/api/pricing/waitlist/route.ts`).
- **Impact:** zero waitlist acquisition; the only demand-validation channel for Pro is closed. 1 existing row predates the middleware behavior.
- **Fix:** add `"/api/pricing/(.*)"` to `isPublicRoute`; confirm `/confirm` and `/remove` token routes are also reachable; add a middleware test that asserts the public allowlist.
- **Effort:** 15 minutes.

#### P0-2. Roadmap size is unbounded → AI/DB amplification
- **Evidence:** `src/app/api/roadmaps/async/route.ts:64-72` accepts `duration`/`time`/`goal`/`level` unvalidated and forwards them. `src/lib/roadmap-sizing.ts:47-57` computes `weeks = ceil(days/7)`, `phases = weeks`, `lessons = weeks * 7` with **no upper clamp**. `src/lib/inngest/functions.ts:228-262` then performs one paced step per phase (2 model calls per phase).
- **Impact:** `duration: "100000 years"` → 36.5M days → 5.2M phases → ~10M model calls and an effectively immortal job. Even the rate limit (5/hour) permits 5 such jobs per account per hour. A single malicious or careless user can exhaust NIM quota and burn real money.
- **Fix:** validate with a schema and clamp: `durationDays` 7–365, `timeMins` 15–480, `phases ≤ 52`, `lessons ≤ 364`; reject non-string/oversized `goal` (>200 chars) and unknown `level`/`style`; clamp again inside `planRoadmapSize` so every caller is safe.
- **Effort:** 1–2 hours including tests.

### P1 — fix before growth

#### P1-1. The core learning loop has never been validated in production
- **Evidence:** 2 `progress` rows, 0 `review_schedule`, 0 `learner_mastery`, 0 `capstone_evidence`, 3 assessments, all-time.
- **Impact:** you cannot claim the product works. Spaced repetition, mastery bands, weakness remediation, and roadmap adaptation are untested paths that could fail on the first real learner (and likely will — they have never run against real data at scale).
- **Fix:** a scripted end-to-end dogfood: create test account → generate roadmap → complete 5 lessons → take quizzes (pass/fail) → verify `weak_topics`, `review_schedule`, `learner_mastery`, analytics → open capstone → submit evidence → replan. Add assertions for row creation. Run it weekly.
- **Effort:** 1 day to build, then 30 min/week.

#### P1-2. Chat request bodies are cast, not validated
- **Evidence:** `src/app/api/chat/route.ts:184` and `:342` — `const { messages, context, threadId, images } = (await req.json()) as {...}`. No caps on array length, per-message size, or total payload. `images` is unbounded and drives one Supabase signed-URL call per entry (`signTutorImages`, lines 23-42).
- **Impact:** a signed-in user can send a multi-megabyte conversation or 1,000 image paths, causing N storage round-trips, model-context blowups, and 60s timeouts. Malformed types produce 500s instead of 400s.
- **Fix:** Zod schema: `messages` ≤ 40, each `content` ≤ 8,000 chars, `images` ≤ 4, `threadId` UUID, `context` whitelisted; reject before any DB/provider call.
- **Effort:** 2–3 hours.

#### P1-3. Rate limiting is non-atomic and partially fail-open
- **Evidence:** `src/lib/rate-limit.ts:74-89` — a `select` counts hits, then an `insert` records the new hit. Concurrent requests all read the same count and all pass. The in-memory fallback is per-instance. Several AI call sites pass `failClosed` only implicitly; the module's own comment says "always fail CLOSED on errors at call sites."
- **Impact:** a burst of 20 parallel roadmap requests can all clear a 5/hour limit; a DB hiccup can silently disable limits. This is the control standing between you and P0-2.
- **Fix:** make the check atomic — a Postgres function that inserts and counts in one statement (or an RPC with `for update`), plus `failClosed = true` for roadmap/lesson/quiz/upload. Consider a 5-minute per-user concurrency cap for generation.
- **Effort:** half a day.

#### P1-4. Upload limits are advisory, not enforced
- **Evidence:** `src/app/api/upload/image/route.ts:52-60` returns `maxBytes: 5MB` and a signed upload URL, but never verifies the uploaded object; `supabase/migrations/010_tutor_images.sql` creates the bucket with **no `file_size_limit` and no `allowed_mime_types`**. MIME type comes from the client.
- **Impact:** a client can upload arbitrary size/type into your private bucket, then have the app sign a read URL for it. Storage-cost abuse and a malware-hosting vector if a signed URL is shared.
- **Fix:** set bucket `file_size_limit = 5242880` and `allowed_mime_types = {image/png,image/jpeg,image/webp,image/gif}`; after upload, `storage.from(...).info(path)` and delete on violation. Enforce server-side before signing the read URL.
- **Effort:** 2 hours + migration.

#### P1-5. Public proof counts placeholder lessons
- **Evidence:** `src/lib/public-proof-server.ts:10-18` counts **all** `lessons` rows. `src/lib/public-proof.ts:8-25` publishes any value ≥100 as "AI lessons generated". Live: 2,668 rows vs **643** with meaningful content and **16** with generated structured content.
- **Impact:** the landing page and pricing page assert a number that is 4× reality (and 166× the structured-content count). This directly violates the standing requirement that social proof be verifiable; it is a trust and consumer-protection risk.
- **Fix:** count `content_json is not null` (or `length(content_md) > 500`), and label it precisely ("lessons with generated content"). Keep the ≥100 publishing threshold. Add a test that a placeholder row does not increment the count.
- **Effort:** 1 hour.

#### P1-6. The service worker caches authenticated API responses
- **Evidence:** `src/app/sw.ts:21` — `runtimeCaching: defaultCache`. Serwist's default cache includes runtime rules for same-origin requests, and `/api/**` GETs are not excluded. The comment above it claims GET APIs are "network-first with a short cache."
- **Impact:** on a shared device, a previous user's roadmap/progress/chat GET response can be served from cache after sign-out; stale authenticated data can also mask bugs.
- **Fix:** prepend an explicit rule: `/\/api\//` → `NetworkOnly` (and `NetworkOnly` for `/api/inngest`). Cache only static assets and public pages.
- **Effort:** 30 minutes.

#### P1-7. No failure alerting or latency tracking for generation
- **Evidence:** `src/lib/alerts.ts` sends email only when an Inngest function exhausts retries. There is no Sentry/exception tracker; PostHog captures client errors only (`src/components/analytics/client-error-reporter.tsx`). No dashboard for model, latency, tokens, or `missingParts`. Job durations are only in the `async_jobs` table.
- **Impact:** the 13-day lesson outage and the 4,120s job were discovered by a human noticing slow UX, not by monitoring. The next regression will be found the same way.
- **Fix:** persist per-job `modelUsed`, `durationMs`, `missingParts`, and token usage into `async_jobs.result`; add a Vercel cron or Inngest cron that alerts when failure rate >10% in 1h or p95 duration > 3× baseline; wire Sentry (or at minimum PostHog server events) for route errors.
- **Effort:** 1 day.

#### P1-8. Pricing advertises limits that are not enforced
- **Evidence:** `src/app/pricing/page.tsx:30-33` — Free: 10 prompts/day, 2 roadmaps/month, 1 adaptation/roadmap, 30 code runs/day. Actual: `src/lib/rate-limit.ts:17-24` — tutor 60/hour (≈1,440/day), roadmap 5/hour (≈120/day), lesson 10/hour, code 30/hour (≈720/day). No monthly counters exist anywhere.
- **Impact:** the comparison table reads as current product behavior while the FAQ calls them "planning targets." A user (or a regulator) reads the table, not the footnote. It also means a free user can consume 12× the advertised roadmap allowance.
- **Fix:** either implement the published limits (daily/monthly counters keyed by UTC day/month) or relabel the table as "planned" and align it with the enforced values. Given Pro is not purchasable, relabeling is the honest, fast option.
- **Effort:** 2 hours (relabel) or 1 day (enforce).

### P2 — next cycle

#### P2-1. RLS is dead weight; `roadmap_review_queue` is fully permissive
- **Evidence:** `supabase/migrations/016_review_queue.sql:22-27` — `for all to authenticated using (true) with check (true)` on read *and* write. Live: the only permissive policies are `public_roadmaps` (intended) and these two.
- **Why it is P2, not P1:** the browser uses the anon key with no Clerk JWT, so no client ever holds the `authenticated` Postgres role. The practical exploit requires a Supabase-issued JWT you do not issue today. But the moment you add direct-client Supabase access (or a Clerk JWT template), any signed-in user can approve, reject, or delete any queue entry.
- **Fix:** replace with `select` scoped to `user_id = auth.jwt()->>'sub'` plus an admin-only policy, or drop the policies entirely (service-role-only writes, like `async_jobs`).
- **Effort:** 30 minutes.

#### P2-2. Job status leaks errors and permits cross-user writes
- **Evidence:** `src/app/api/roadmaps/status/[jobId]/route.ts:82-83` returns `job.error` **before** any ownership check. Lines 124-137 can mark any `processing` job failed. Job IDs are UUIDv4, so guessing is impractical, but IDs can leak via logs, support tickets, or shared screenshots.
- **Impact:** information disclosure (internal/provider error text) and a denial-of-service primitive against another user's running job.
- **Fix:** select `user_id` with the job row and verify ownership before returning status/error or writing the stale-fail. Add an `owner_id` column to `async_jobs` (currently absent) so ownership is explicit rather than inferred through roadmap/lesson.
- **Effort:** 2 hours + migration.

#### P2-3. Errors from infrastructure are persisted verbatim
- **Evidence:** `src/app/api/roadmaps/async/route.ts` writes `` `Inngest trigger failed: ${message}` `` into `async_jobs.error` and returns it to the client. Provider errors elsewhere are mapped through `classifyJobError`, but this path is raw.
- **Impact:** internal endpoint names, project IDs, and stack-adjacent detail can reach users.
- **Fix:** store the raw message in a server-only `debug_error` column/log, return a fixed friendly string.
- **Effort:** 30 minutes.

#### P2-4. CSP relies on `'unsafe-inline'` for scripts
- **Evidence:** `src/middleware.ts:41` — `script-src 'self' 'unsafe-inline' ...`.
- **Impact:** the primary XSS mitigation is substantially weakened. React escapes by default, so this is not an open hole, but any HTML injection becomes script execution.
- **Fix:** move to a nonce-based CSP (`next/headers` nonce) and remove `'unsafe-inline'`; keep `'strict-dynamic'` if Clerk widgets require it.
- **Effort:** half a day.

#### P2-5. No backup/restore or migration discipline
- **Evidence:** no backup/DR documentation; `supabase/migrations/` contains **two `010_` files** (`010_rate_limits.sql`, `010_tutor_images.sql`); 26 files for 28 tables; no `supabase` CLI config, no CI migration check. The README tells operators to paste SQL into the dashboard.
- **Impact:** schema drift between environments is likely; a restore has never been rehearsed; duplicate prefixes make ordered application ambiguous for anyone but the original author.
- **Fix:** rename to `010a/010b` (or renumber 026+ going forward), add a `supabase/config.toml`, run migrations through CI against a shadow DB, and document a restore drill (Supabase PITR + storage).
- **Effort:** 1 day.

#### P2-6. Worst-case lesson chain can take ~6 minutes
- **Evidence:** `src/lib/inngest/lessons.ts` — foundation (100s) → 3 parallel parts (100s) → up to 3 repairs in parallel (100s) → quality regeneration (70s). Each step is its own invocation, so the 300s Vercel cap is not violated, but the *user-visible* job can run ~6 minutes.
- **Impact:** users on slow connections see a long spinner; a 6-minute job is also a 6-minute window for the stale guard to mis-fire if `totalPhases` defaults are wrong for lesson jobs.
- **Fix:** cap total lesson wall-clock at 4 minutes; skip repair when the merged score is already ≥85; show partial content with a "finishing" state instead of blocking the reader.
- **Effort:** half a day.

#### P2-7. No E2E tests; route handlers are largely untested
- **Evidence:** 431 tests across 52 files, all unit-level (`src/lib`); no Playwright/Cypress, no integration tests against route handlers. CI runs lint, typecheck, unit tests — not `build`.
- **Impact:** the bugs that actually shipped (waitlist 401, missing lesson parts, middleware allowlist) are invisible to the current suite. The lesson fix was validated by a manual production job.
- **Fix:** add Playwright for 4 flows (sign-in → generate → read lesson → quiz → review); add `npm run build` to CI; add route-handler tests for auth/ownership using a mocked Supabase.
- **Effort:** 2 days.

#### P2-8. Single AI vendor with no cross-provider fallback
- **Evidence:** the entire pipeline routes through NVIDIA NIM (`src/lib/nim.ts`, `src/lib/ai-router.ts`); hedging happens between *models on the same provider/account*. Earlier Gemini fallbacks were removed.
- **Impact:** a NIM account issue (the NVCF `404 Function not found` incident) or a quota change takes down all generation. There is no second vendor.
- **Fix:** keep the primary path, but add one independent provider (or a self-hosted model) behind the same `chatForFeature` interface for roadmap and lesson generation; test quarterly with `scripts/check-ai.mjs`.
- **Effort:** 1–2 days.

## 6. Security assessment (detail)

**Verified good**
- No secrets in git: `.env*` is ignored and `git ls-files` contains no env file.
- Service-role key is server-only; the browser client uses the anon key and cannot write.
- Clerk webhook signature is verified; Inngest requests are signature-verified by the SDK.
- Code runner is properly bounded: 4,000-char source, 20s timeout, 30 runs/hour, language allowlist (`src/app/api/code/run/route.ts`).
- Account deletion exists and deletes the Clerk identity first (`src/app/api/me/account/route.ts`).
- HSTS, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` all ship.
- No `dangerouslySetInnerHTML` with user content — only JSON-LD and one static install script.
- No SSRF surface found: no route fetches a user-supplied URL.
- No P0 authentication bypass: 40 of 45 routes enforce `auth()`; the other 5 are webhook, Inngest, health, and the three waitlist routes (the last three are the P0-1 bug).

**Structural risk to accept consciously**
RLS provides no runtime protection because all queries use the service role. Mitigations that should become policy:
1. Every new route that touches a user-owned table must call a shared `userOwns*` helper; add a lint/rule or code-review checklist.
2. Add integration tests that assert 404 (not 403) for cross-user IDs on every such route.
3. If direct-client Supabase is ever introduced, fix P2-1 first and re-scope every policy to `auth.jwt()->>'sub'`.

**Residual attack surface**
- Prompt injection: learner goals, lesson titles, and tutor images flow into prompts; outputs are rendered as structured blocks, not executed. Risk is content manipulation, not code execution. Acceptable with the current quality gate.
- `/api/chat` uses a spoofable `x-forwarded-for` fallback only when `userId` is null — middleware already blocks that, so it is dead code. Clean it up.
- Rate-limit keys include the user ID; no shared-IP starvation observed.

## 7. Reliability assessment

**What is now healthy**
- Lessons: 122 completed / 0 failed in 30 days; post-fix runs at 49–69s with complete parts.
- Absolute deadlines plus hedged fallback removed the multi-minute hangs (worst pre-fix job: 4,120s).
- Stale-job sweep runs every 30 minutes and scales its cutoff to planned phase count.
- Roadmap jobs write the roadmap row early so progress is observable.

**What still worries me**
1. **Failure detection is human.** No alert when a job fails or slows down. P1-7.
2. **Quiz generation is the least-observed worker.** 43 non-lesson failures in 30 days; quiz uses a 90s deadline with retries but has no `missingParts`-style completeness signal.
3. **Repo/watchdog asymmetry.** The sweep marks jobs failed after a timeout, but nothing retries them automatically; users must press Generate again.
4. **Cold-start variance.** NIM latency is the dominant variable; there is no queueing or admission control beyond the hourly limit.

**Suggested SLOs (start measuring, then commit)**
- Lesson p95 end-to-end < 120s; < 1% jobs with `missingParts`.
- Roadmap p95 < 4 minutes; < 5% failure rate.
- Chat first token < 2s; < 1% 5xx.
- API availability > 99.5% monthly.

## 8. Data, privacy, and compliance

- **PII stored:** Clerk ID, email, name, avatar URL; learner goals, chat content, uploaded screenshots, quiz results, progress. That is standard for this product.
- **Retention:** account deletion cascades from `users`; uploaded images are **not** deleted with the account (the bucket is separate). That is a GDPR/CCPA gap — deletion must remove the user's `tutor-images` prefix.
- **Consent/analytics:** a consent banner exists and gates PostHog (`src/components/analytics/consent-banner.tsx`); verify it defaults to off and that server-side PostHog events respect consent.
- **Data export:** pricing claims "JSON data export"; confirm the route/page exists and covers chat + evidence, not just progress.
- **Children:** pricing/terms correctly state 13+ and parental consent for 13–17. Keep that; do not add under-13 signup.
- **Backups:** rely on Supabase PITR; no rehearsal evidence. P2-5.

## 9. Performance and unit economics

- Roadmap: 8 phases / 56 lessons in **2m50s** (verified). Lesson: **62s** (verified).
- Route budgets are 60s; Inngest 300s. The design correctly keeps each step under ~100s.
- **No token accounting.** You know how long a job took, not how many tokens or dollars it cost. For a free product with a planned $4.99 Pro tier, that is the single most important missing business metric.
- **Rough cost model to build next:** per lesson ≈ 4 calls × (1.8k–2.6k output tokens + prompt); per roadmap ≈ phases × 2 calls. Persist `prompt_tokens` / `completion_tokens` from the provider response (NIM returns `usage`) into `async_jobs.result`. Without this you cannot price Pro, set fair-use limits, or detect abuse.
- **Waste to remove:** the quality-gate regeneration runs even when a part is missing and the merged score is already high; repairs run for non-practice parts that add little. Both add cost for marginal quality.
